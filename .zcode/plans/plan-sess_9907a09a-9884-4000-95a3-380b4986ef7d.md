# AI-Marking 三个高危漏洞修复方案

修复上一轮确认的三个高危：
- **#1 全站无鉴权** → 共享访问令牌（已确认：不建账号、前端与 MCP 共用同一令牌、从 backend/.env 读取）
- **#2 worker 重跑覆盖已确认成绩** → run_marking_pipeline 状态机守卫
- **#3 MCP score 未校验** → McpAssessmentRequest 总分一致性校验

无新依赖、无数据库迁移、无新表、无账号体系。

---

## Part 1 — 共享访问令牌（高危#1，最小方案）

### 后端

1. **`backend/app/core/config.py:46`**：新增 `ACCESS_TOKEN: str = ""`（空 = 鉴权关闭，保持现状向后兼容；使用时手动在 `backend/.env` 填 `secrets.token_urlsafe(32)` 生成的令牌）。

2. **新增 `backend/app/api/auth.py`**（约 35 行）——纯 ASGI 中间件 `AccessTokenMiddleware`（避免 `BaseHTTPMiddleware` 缓冲 SSE 流式响应）：
   - `settings.ACCESS_TOKEN` 为空 → 全部放行（现有 dev/测试/幂等行为不破坏）
   - 豁免路径：`/api/health`、`/api/mcp/health`（start.sh / start.prod.sh 与 MCP 客户端探活依赖，不能锁）
   - 令牌来源：`Authorization: Bearer` / `X-Access-Token` header / `?access_token=` 查询参数（SSE/PDF/图片等无法带 header 的浏览器原生请求用）
   - `secrets.compare_digest` 常量时间比较，失败回 401 JSON

3. **`backend/app/main.py`**：注册中间件；新增公开端点 `GET /api/auth/verify`（200/401，供前端令牌门校验，无令牌时不触发 toast）。

4. **`backend/app/mcp/client.py:36-41`**：读 `settings.ACCESS_TOKEN`，非空时给 httpx `headers={"Authorization": f"Bearer {token}"}`。`/api/mcp/health` 在豁免列表，Codex / setup-codex-mcp 零改动。

5. **`backend/.env.example`**：补 `ACCESS_TOKEN` 说明。

### 前端

6. **`frontend/src/api/client.ts`**：新增请求拦截器，有令牌时附 `X-Access-Token` header；响应拦截器对 401 区分——已存令牌→提示"登录已过期"并清令牌回令牌门，未存令牌→静默。

7. **`frontend/src/App.tsx`**：最简令牌门——无令牌时渲染"输入访问令牌"小卡片（非独立登录页），提交后 `GET /api/auth/verify` 通过再渲染应用；后端鉴权关闭时 verify 直接 200，照常放行。令牌存 localStorage。

8. **4 处浏览器原生请求追加 `?access_token=`**（令牌门生效的必要条件，每处一行）：
   - `frontend/src/api/submissions.ts:259`（EventSource SSE）
   - `frontend/src/components/PdfViewer.tsx:46`（iframe PDF）
   - `frontend/src/pages/QuestionsPage.tsx:309`（题目 PDF 链接）
   - `frontend/src/pages/ReviewPage.tsx:162`（代码资产下载链接）

### 配套（强烈建议）

9. **`frontend/vite.config.ts:33` 与 `:43`**：`server.host` / `preview.host` 由 `true` 收紧为 `127.0.0.1`——纯配置、零代码，直接关掉 dev 模式局域网暴露（最现实的风险面）。

## Part 2 — 状态机守卫（高危#2）

### 后端 `backend/app/services/marking.py`

1. 定义 `_PIPELINE_OWNED_STATES = {pending, ocr_processing, ocr_done, agent_grading, agent_reviewing, agent_revising, awaiting_codex}`。
2. **入口守卫**（`db.get` 之后，~`:107`）：`sub.status` 不在集合中 → log + `return`（不抛异常——worker 在 `_execute` 正常返回后调 `complete_job` 删除僵尸任务行，避免无限重认领）。
3. **终态写保护**：最终 `ready_for_review` 写入（`:226-240`）与 `_mark_failed`（`:54-72`）先 `with_for_update` 重读当前状态，若已是 `ready_for_review`/`reviewed` → 跳过写入并返回（镜像 `question_replace.py:83-91` 已有的"重读比对"模式），关闭教师中途 finalize 的竞态窗口。
4. **worker 死信保护**：`worker.py:120-124` `_mark_target_failed` 同样加守卫——目标已是 `ready_for_review`/`reviewed` 时不再覆盖为 `failed`。
5. **retry 不受影响**（已核实）：`retry_submission` 先 `failed → pending` 再入队（`submissions.py:310-312`），守卫放行 `pending`。

### 测试 `backend/tests/test_marking.py`

6. 单元：submission 预置 `ready_for_review`（及 `reviewed`）→ 调 `run_marking_pipeline`（fake `ocr_pdf`/`run_marking_agent` 置哨兵）→ 断言 fake 未被调用、状态与 score/ai_suggestion 未被改写。
7. worker 级：`new_submission_marking_job` + `claim_next_job` + `worker._run_claimed` → 断言 `ready_for_review` 存活且 job 行被删除（复用现有 `marking_session_factory` 模式）。

## Part 3 — MCP 分数一致性校验（高危#3）

### 后端 `backend/app/schemas/mcp.py`

1. 给 `McpAssessmentRequest` 加 `@model_validator(mode="after") totals_are_consistent`，与 `backend/app/schemas/scoring.py:51-59` 的 `GradingResult` 完全一致（ε=0.01）：
   - `score ≤ max_score`
   - `sum(detail.score) == score`
   - `sum(detail.max_score) == max_score`
2. 已核实现有所有构造点（`test_mcp_server.py:116`、`test_question_rubric.py:44`、`test_mcp_api.py:171`）均自洽，无破坏。`validate_assessment_details`（rubric 全覆盖）+ `max_score == total` 已在服务层，schema 边界校验补上缺口后 `quality_checks["arithmetic_valid"]=True` 变为真构造。

### 测试

3. 单元：`McpAssessmentRequest(score=120, max_score=100, ...)` → `pytest.raises(ValidationError)`（`test_mcp_server.py`）。
4. 端到端：`backend/tests/test_mcp_api.py` 扩展 save 测试（沿用 `test_package_paginates_and_compact_save_enforces_handle` 的 package→handle→rubric 流程），提交 `score=120/max_score=100` 与"总分≠明细和"各断言 422。
